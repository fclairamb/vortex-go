Versus the Rust implementation

Rust is the reference: the format is defined by its code, and it judges ours. This page says what is the same, what differs, and how fast and how small we are next to it. Every ratio is shown, the ones where we lose first.

What is the same

  • The file format. The same files, in both directions.
  • The edition. We target the default core edition of the pinned upstream release.
  • Who judges. The Rust reader reads every file we write and gives back the values we wrote. Our reader is checked against the Rust one on every file of the corpus, including the fixtures of every published release.

What differs

  • What the writer emits. Bit-packing, frame of reference, zigzag, run-length, run-end, dictionary, sequence, constant, sparse, ALP, ALP-RD, FSST, OnPair, decimal byte parts, datetime parts, zstd and, in compact mode, Pco. The matrix below has the rest.
  • Not byte-identical. The format leaves layout, segment order and encoding choice to the writer. Our files are not the Rust writer's.
  • Non-goals. A query engine (projection and filters only, no joins or aggregations), Arrow in the core module, the preview and unstable editions and third-party encodings, big-endian platforms, object store clients (bring an io.ReaderAt), the Union type.
  • Self-contained. No cgo, no assembly. Nothing to install next to the Go toolchain.

Which one to use

  • A Go program that reads or writes Vortex files: use vortex-go. No cgo, no sidecar, a few lines.
  • The fastest scan, or an encoding we do not write: use the Rust implementation, from Rust or through its bindings. The table above says by how much.
  • A query engine, joins, aggregations or Arrow: use the Rust implementation and its engines. We do projection and filters only.
  • Files that both read: no choice to make. What one writes the other reads.
